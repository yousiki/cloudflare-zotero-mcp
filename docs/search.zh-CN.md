# 搜索指南

[English](search.md) | **简体中文**

服务器提供两个行为刻意不同的搜索工具。本文解释如何在两者之间选择、语义索引如何与文献库保持
同步，以及如何解读语义分数。

## 选哪个搜索工具

`zotero_search` 走 Zotero Web API。它匹配字面文本和字段——标题、作者、日期、摘要、标签、
条目类型、分类集、Better BibTeX citation key——用 `sort`/`direction` 排序，用 `qmode` 控制
文本匹配范围，看到的是文献库此刻的状态，无匹配时返回空。已知作者、标题片段、精确短语，或者
需要排序时，用它。

`zotero_semantic_search` 走 Cloudflare AI Search。当你的问题是关于一个主题而不是一个已知
条目时用它：它能找到与查询没有任何共同措辞的论文。它按相近度排名而不是过滤，所以要读分数和
`note`，不要默认结果都相关。它无法排序，并且落后文献库最多一个同步周期——cron 每六小时运行
一次，几分钟前刚添加的条目 `zotero_search` 能找到而它找不到，直到 `zotero_reindex` 补上差距。
当部署没有绑定 AI Search 时，该工具会抛错并指明改用 `zotero_search`。

两个工具都无法召回 PDF 正文，而 `zotero_search` 正是容易让人误会的地方：
`qmode: "everything"` 确实会搜索 Zotero 的全文索引，但 Zotero 用*附件*来响应这种命中，而附件
默认被排除，除非 `itemType` 另有指定——所以只出现在 PDF 正文里的短语什么也搜不到。传
`itemType: "attachment"` 才能找到它，然后自己查它的 `parentItem`。这是长期以来的行为，AI
Search 迁移和工具拆分都没有改变它。

## 索引是异步的

同步为每个条目上传一份文档，命名为 `<itemKey>.md`。`upload` 对该名称是 upsert，因此条目变更
会替换自己的文档而不是累积副本——并且文档一入队它就返回。所以 `zotero_reindex` 返回的
`complete: true` 意味着所有变更都已*提交*，而不是已可搜索：`submitted` 统计本次 AI Search
接受的文档，`backlog` 是它仍在处理的（`null` 表示无法询问 AI Search——和零不是一回事），
`failed` 是无法索引的，`remaining` 是留给下一次运行的变更条目。cron 触发器每六小时运行同一个
同步，每次 100 个条目；每个条目是一次上传，每次上传是一个 subrequest，所以超出批量的部分留到
下一次运行，而不是撞上限额。

删除则反过来。`items.delete` 接受的是 AI Search 自己的不透明条目 id 而不是文档名，所以要靠
分页遍历实例的条目列表来解析 id。Zotero 的 `/deleted` feed 也会报告附件、笔记和批注——它们
从未被上传过——所以"key 没有对应文档"是正常情况而不是错误。无法完成的扫描则会抛错：库游标在
删除返回后就会前进，如果这里谎报成功，那些文档就永远留在索引里了。

## 解读语义分数

语义检索是混合的，不是纯向量：AI Search 用 BM25 和向量搜索同一批文档，用 RRF 融合两个排名，
再用 `@cf/baai/bge-reranker-base` 重排序。文档按 512 token 分块——这是 `@cf/baai/bge-m3` 在
Workers AI 上的输入上限，也足以让实测条目的文档是单个分块，所以一个条目通常只占一个结果槽位。
之所以混合，是因为调用者选这个工具是*替代* `zotero_search`，从不与之并用——在两者之间选择是
一次猜测，所以这个工具必须自带词法精度。像 "Sparse VideoGen2" 这样的精确名称，词法索引能直接
匹配，而向量距离只能近似。这一半也是 `keyword_match_mode` 设为 `or` 而不是服务默认 `and` 的
原因：要求自然语言问题的每个词都出现在同一个分块里，会在这个工具正需要的措辞上清空 BM25 侧，
而且永远匹配不到中文查询——关键词索引是 Porter 词干化的。

代价是有些行没有分数。报告的 `score` 是匹配的余弦一半（`scoring_details.vector_score`），
绝不是融合分数：下文的分数带是在余弦上测量的，混入 BM25 排名的数值不在那个刻度上。混合检索
不会为每个结果报告距离，所以有些行完全没有 `score`——缺失意味着"该结果没有报告相似度"，绝不是
零。输出统计全部三种情况：`scored` 是带分数的行数，`belowThreshold` 是*其中*低于 `minScore`
的行数，`unscored` 是没有分数的行数，并附一条 note 说明分数下限无法应用于多少行。
`belowThreshold` 要对照 `scored` 读，绝不要对照 `total`。

低分候选会被保留并报告而不是丢弃，因为 `minScore` 是建议性的。检索按距离排名而不是过滤，
所以有结果并不说明相关：文献库不覆盖的查询照样拿回最近邻文档。工具仍可能返回空——索引未填充、
过滤器丢弃了所有候选、或者匹配的条目 Zotero 已经没有了——每种情况都在 `note` 里报告，而不是
被抹平。

`minScore`（默认 0.5）是一个只报告不丢弃的建议性下限——设得太高的下限会不留痕迹地隐藏真实
命中，这也是后端自己的 `match_threshold` 被固定为 0 的原因，检索和重排序都是如此，而不是留在
其默认值 0.4。

分数带，在一个约 1000 条目的 ML 文献库上用 `@cf/baai/bge-m3` 测量：与文献库毫无关系的查询是
0.315–0.332；文献库并不覆盖的相邻领域是 0.498–0.525；主题相关的，英文 0.552–0.596，中文
0.566–0.593，所以跨语言查询没有代价。中间两个区间几乎相接，这就是 0.5 只警告不过滤的原因：
读分数的分布而不是任何单个值，因为分数普遍偏低*且*几乎相同意味着索引拿不出任何东西。

## 过滤器

过滤器同样收窄语义结果，且在两处生效。只有 `itemtype` 和 `year` 被下推到搜索本身：AI Search
每个实例只允许五个自定义元数据字段，没有数组类型，且改动 schema 会重建整个库的索引。`tags`、
分类集归属、取反的条目类型和 `since` 在之后强制执行，由反正都要获取匹配条目的 Zotero
`itemKey` 查询来完成——`collectionKey` 对照 `data.collections`，即直接归属，正是
`/collections/<key>/items` 不带 `recursive=1` 时返回的内容。`fromYear`/`toYear` 边界也在那里
复查，用与索引存储相同的"日期前四位数字"解析，因此下推的过滤器和本地过滤器不会对同一条目
产生分歧。因为这些检查在后端应用自己的 limit 之后运行，被过滤的查询会请求
`FILTER_OVERSHOOT`——三——倍于所需的候选；否则一个标签就把请求的 20 个结果变成 2 个。
`zotero_search` 对年份边界做同样的事，那是它唯一在本地应用的过滤器。语义工具在途中丢弃的
匹配——被过滤掉的，或索引写入后已从 Zotero 消失的——都计入它的 `note`。

## 限制与排序

两个工具接受的参数也不同。`zotero_search` 的 `limit` 上限是 100；`zotero_semantic_search`
到 50 为止，因为那是 AI Search 单次查询的上限，且一个条目的文档通常是一个分块。"通常"不是
"总是"：`documentText` 上限 6000 字符，约 1200 token，所以摘要特别长的条目仍会拆成两三块、
占用不止一个槽位——一页结果可能比请求的少几条。`includeTrashed` 只存在于 `zotero_search`：
索引里没有回收站条目，这个开关不可能改变语义结果。同理，那里的 `itemType` 也够不到附件、
笔记和批注——无论传什么，它们从不被索引。

语义侧不提供排序：结果保持返回时融合、重排后的顺序，一个条目按其最先出现的分块排名。
`sort`、`direction`、`qmode` 和 `citationKey` 只存在于 `zotero_search`。
